# Wimmer — Database Schema

## Multi-Tenant Design Philosophy

Wimmer's database is designed around a strict multi-tenant model: every resource belongs to an organisation, and every query at the service layer must include an `organisation_id` filter. There are two levels of isolation:

1. **Service layer isolation (primary):** Every service method that accesses tenant data receives and enforces `organisation_id`. The `OrganisationService.assert_member()` call is the gatekeeper.

2. **PostgreSQL Row-Level Security (planned, defence-in-depth):** RLS policies on each resource table ensure that even a service layer bug cannot return rows from a different tenant. This is not yet implemented in the MVP but is documented here as planned.

---

## Schema Overview

```
users
  └── organisation_members (many-to-many join)
        └── organisations
              └── properties
                    ├── daily_performance
                    ├── demand_forecasts
                    └── recommendations
                          └── (approved_by → users)

organisations
  ├── organisation_members
  ├── market_signals
  ├── recommendations
  └── audit_logs
```

---

## UUID Primary Keys

All tables use UUID v4 primary keys generated by the application (`uuid.uuid4()`), not sequential integers.

**Rationale:**
- UUIDs do not leak information about the number of records (sequential IDs reveal row counts)
- Safe to generate in the application without a database round-trip
- Required for distributed systems where multiple nodes may insert simultaneously
- No cross-tenant enumeration attacks via integer ID guessing

The PostgreSQL `UUID` type is used directly (not stored as `varchar`), which is efficient and correct.

---

## Timezone-Aware Timestamps

All `created_at` and `updated_at` columns use `DateTime(timezone=True)`. PostgreSQL stores these as `TIMESTAMPTZ`.

**Rationale:** Properties may be located in different timezones. The `properties.timezone` column captures the local timezone (e.g., `Europe/Berlin`, `Europe/London`). Storing all timestamps in UTC with explicit timezone information prevents ambiguity when reasoning across timezones.

---

## Common Patterns

Every table shares two mixins:

**UUIDMixin:**
```sql
id  UUID  PRIMARY KEY  DEFAULT uuid_generate_v4()
```

**TimestampMixin:**
```sql
created_at  TIMESTAMPTZ  NOT NULL  DEFAULT now()
updated_at  TIMESTAMPTZ  NOT NULL  DEFAULT now()
```

`updated_at` is set via SQLAlchemy's `onupdate=func.now()` on every UPDATE.

## Table Definitions

### 1. users

Stores individual user accounts. Users are global — they join organisations via `organisation_members`.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | UUID | PK | UUID v4, application-generated |
| `email` | VARCHAR(255) | NOT NULL, UNIQUE, INDEX | User email address, used for login |
| `hashed_password` | VARCHAR(255) | NOT NULL | bcrypt hash, never stored in plain text |
| `full_name` | VARCHAR(255) | NOT NULL | Display name |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT true | Whether the account is enabled |
| `is_superuser` | BOOLEAN | NOT NULL, DEFAULT false | Reserved for Wimmer platform administrators |
| `is_verified` | BOOLEAN | NOT NULL, DEFAULT false | Email verification status (feature planned) |
| `created_at` | TIMESTAMPTZ | NOT NULL | Auto-set on insert |
| `updated_at` | TIMESTAMPTZ | NOT NULL | Auto-updated on change |

**Indexes:** `ix_users_email` (unique)

**Notes:**
- Passwords are hashed with bcrypt (passlib, work factor 12)
- `is_superuser` is not exposed through any public API endpoint

A tenant boundary. Each organisation represents a hotel group, restaurant group, or other business entity.

| Column | Type | Constraints | Description |

**Indexes:** `ix_organisations_slug` (unique)

### 3. organisation_members

Many-to-many join between users and organisations, with a role column.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | UUID | PK | — |
| `organisation_id` | UUID | NOT NULL, FK → organisations(id) CASCADE | — |
| `user_id` | UUID | NOT NULL, FK → users(id) CASCADE | — |
| `role` | VARCHAR(50) | NOT NULL, DEFAULT 'viewer' | Enum: owner, admin, analyst, viewer |
| `is_active` | BOOLEAN | NOT NULL, DEFAULT true | Soft membership deactivation |
| `created_at` | TIMESTAMPTZ | NOT NULL | — |
| `updated_at` | TIMESTAMPTZ | NOT NULL | — |

**Role semantics:**

| Role | Capabilities |
|------|-------------|
| `owner` | Full access, can transfer ownership, cannot be removed by others |
| `admin` | Full access except ownership transfer, can manage members |
| `analyst` | Read/write access to data, forecasts, recommendations |
| `viewer` | Read-only access |

**Notes:**
- When an organisation is created, the creating user is automatically assigned the `owner` role
- CASCADE delete: if a user is deleted, their memberships are removed

**Indexes:** `ix_properties_organisation_id`

**Notes:**

### 5. daily_performance

The core fact table. One row per property per calendar day.

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | UUID | PK | — |
| `property_id` | UUID | NOT NULL, FK → properties(id) CASCADE, INDEX | — |
| `date` | DATE | NOT NULL, INDEX | Calendar date of the record |
| `rooms_available` | INTEGER | NOT NULL | Total rooms available (may differ from total_rooms due to maintenance) |
| `rooms_sold` | INTEGER | NOT NULL, DEFAULT 0 | Rooms occupied on this date |
| `occupancy_rate` | NUMERIC(5,4) | NOT NULL, DEFAULT 0 | Decimal 0–1 (e.g. 0.7843 = 78.43%) |
| `room_revenue` | NUMERIC(12,2) | NOT NULL, DEFAULT 0 | Total room revenue in local currency |
| `adr` | NUMERIC(10,2) | NOT NULL, DEFAULT 0 | Average Daily Rate (room_revenue / rooms_sold) |
| `revpar` | NUMERIC(10,2) | NOT NULL, DEFAULT 0 | Revenue Per Available Room (room_revenue / rooms_available) |
| `cancellations` | INTEGER | NOT NULL, DEFAULT 0 | Number of cancellations on this date |
| `new_bookings` | INTEGER | NOT NULL, DEFAULT 0 | Number of new bookings made on this date |
| `source_file` | VARCHAR(255) | nullable | Filename of the import source |
| `data_source` | VARCHAR(50) | NOT NULL, DEFAULT 'upload' | Source type: upload, pms_sync, manual, demo |
| `is_validated` | BOOLEAN | NOT NULL, DEFAULT false | Whether the row passed validation checks |
| `created_at` | TIMESTAMPTZ | NOT NULL | — |
| `updated_at` | TIMESTAMPTZ | NOT NULL | — |

**Indexes:** `ix_daily_performance_property_id`, `ix_daily_performance_date`

**Unique constraint:** `uq_daily_performance_property_date` — `(property_id, date)`. One record per property per day. Import will upsert on this constraint.

**Notes:**
- `occupancy_rate` is stored as a decimal fraction, not a percentage, to avoid ambiguity
- `adr` and `revpar` are stored as computed values (redundant but efficient for query performance)
- `NUMERIC(12,2)` for monetary values: handles up to €9,999,999,999.99 — sufficient for any hotel
- `is_validated` must be true for the forecasting engine to use the row

### 7. demand_forecasts

One row per (property, metric, forecast_date, target_date) combination. Forecast runs for the same metric on the same day replace each other (old rows are deleted before inserting new ones).

| Column | Type | Constraints | Description |
|--------|------|-------------|-------------|
| `id` | UUID | PK | — |
| `property_id` | UUID | NOT NULL, FK → properties(id) CASCADE, INDEX | — |
| `forecast_date` | DATE | NOT NULL, INDEX | Date the forecast was generated |
| `target_date` | DATE | NOT NULL, INDEX | Date being predicted |
| `model_name` | VARCHAR(100) | NOT NULL | Model used: seasonal_naive, moving_average, insufficient_data |
| `metric` | VARCHAR(50) | NOT NULL | Enum: occupancy, revenue, adr, revpar, rooms_sold |
| `predicted_value` | NUMERIC(12,4) | NOT NULL | Point forecast |
| `lower_bound` | NUMERIC(12,4) | nullable | 95% prediction interval lower bound |
| `upper_bound` | NUMERIC(12,4) | nullable | 95% prediction interval upper bound |
| `confidence_level` | NUMERIC(4,3) | nullable | Confidence level (default 0.95) |
| `mae` | NUMERIC(10,4) | nullable | Mean Absolute Error from backtest |
| `rmse` | NUMERIC(10,4) | nullable | Root Mean Squared Error from backtest |
| `wape` | NUMERIC(6,4) | nullable | Weighted Absolute Percentage Error from backtest |
| `created_at` | TIMESTAMPTZ | NOT NULL | — |
| `updated_at` | TIMESTAMPTZ | NOT NULL | — |

**Indexes:** `ix_demand_forecasts_property_id`, `ix_demand_forecasts_target_date`

**Notes:**
- `NUMERIC(12,4)` provides 4 decimal places for occupancy (which ranges 0–1) while accommodating large revenue values
- Accuracy metrics are populated only when the backtesting holdout had sufficient data (≥28 days)

## Planned: Row-Level Security

The following RLS design is planned for a future migration. It is documented here to record the intended design before implementation.

**Principle:** Each application connection will set a session variable `app.current_org_id` before executing queries. RLS policies will enforce that only rows matching this variable are returned.

```sql
-- Enable RLS on each resource table
ALTER TABLE properties ENABLE ROW LEVEL SECURITY;
ALTER TABLE daily_performance ENABLE ROW LEVEL SECURITY;
ALTER TABLE demand_forecasts ENABLE ROW LEVEL SECURITY;
ALTER TABLE recommendations ENABLE ROW LEVEL SECURITY;
ALTER TABLE market_signals ENABLE ROW LEVEL SECURITY;
ALTER TABLE audit_logs ENABLE ROW LEVEL SECURITY;

-- Example policy for properties
CREATE POLICY tenant_isolation ON properties
    USING (organisation_id = current_setting('app.current_org_id')::uuid);
```

**Session variable pattern:**
```python
# In SQLAlchemy event hook, before each query:
db.execute(text("SET app.current_org_id = :org_id"), {"org_id": str(org_id)})
```

**When this will be implemented:** After the service layer isolation is comprehensively tested and before any external production deployment. RLS adds a meaningful safety net but should not be the first line of defence.

## Decimal Precision Reference

| Column | Type | Range | Precision |
|--------|------|-------|-----------|
| `occupancy_rate` | NUMERIC(5,4) | 0.0000–1.0000 | 4 decimal places (0.01% resolution) |
| `latitude`, `longitude` | NUMERIC(9,6) | ±180.000000 | ~11cm geographic precision |
| `room_revenue`, `expected_revenue_impact` | NUMERIC(12,2) | Up to €9.99B | 2 decimal places (cent precision) |
| `adr`, `revpar` | NUMERIC(10,2) | Up to €99,999,999 | 2 decimal places |
| `predicted_value`, `lower_bound`, `upper_bound` | NUMERIC(12,4) | — | 4 decimal places (supports both occupancy fractions and revenue) |
| `confidence_level`, `confidence_score` | NUMERIC(4,3) | 0.000–1.000 | 3 decimal places |
| `expected_occupancy_impact` | NUMERIC(5,4) | ±1.0000 | 4 decimal places |
| `mae`, `rmse` | NUMERIC(10,4) | — | 4 decimal places |
| `wape` | NUMERIC(6,4) | 0.0000–99.9999 | 4 decimal places |

**Why not FLOAT?** IEEE 754 floating point introduces rounding errors that are unacceptable for financial calculations. `NUMERIC` (exact decimal arithmetic) is used for all monetary values and rates.
